## 대표 프로젝트

### [여담](https://github.com/100-hours-a-week/KTB4-2nd-AI) | 여행 사진 자동 정리, 자연어 검색 서비스 (2026.08 - 2026.11)

- 카카오테크 부트캠프 팀 6명(풀스택 3명, 클라우드 1명, AI 2명), AI 파트: 사진 자동 정리, 자연어 사진 검색, 여행 스토리 생성, 모델 서빙
- 기술: Gemma 4 31B, Qwen3-VL-Embedding-2B, vLLM, LangGraph, Qdrant, FastAPI, Kafka, Redis, AWS EC2(L4), RunPod(A40)
- 개발 기록: [팀 블로그 사진 정리 속도 개선 시리즈 4편](https://medium.com/yeodam-tech)

**프로젝트 소개**

- 여행 사진을 올리면 장소별 폴더로 자동 정리하고, "9/10에 찍은 사진", "거기서 뭐 먹었지?" 같은 자연어로 사진을 찾거나 질문하며, 고른 사진으로 여행 스토리를 만들어 주는 서비스

**평가 체계를 먼저 구축해 모든 개선을 같은 기준으로 판정**

- 정리: 3개 기기(iPhone, 갤럭시, 디지털카메라) 사진 200장에 정답 장소를 직접 라벨링, B-cubed F1과 ARI로 자동 채점
- 검색: 개인 사진 검색 벤치마크 PhotoBench의 질의 분류와 거절 지표를 차용해 7개 유형 51문항 테스트셋 구축(정답 없는 질문, 프롬프트 인젝션 포함), 순위(nDCG@10), 반환(F1), 거절(Reject-F1) 분리 측정
- 분석: 기준선 실패 문항을 질의 해석, 후보 거르기, 임베딩 순위, 결과 자르기 단계별로 분류해 개선 순서 결정
- 재현: 고정 채점 스크립트로 변경마다 같은 데이터와 조건에서 재측정, 임계값과 지시문은 별도 개발셋에서만 선택, 반복 측정 편차 안의 변화는 개선에서 제외

**위치 정보 없는 사진의 장소 추정**

- 문제: GPS가 없는 갤럭시, 디지털카메라 사진 71장이 장소를 정하지 못한 미분류로 남음
- 해결: 규칙 배정 뒤 남은 사진은 LangGraph 기반 정리 에이전트가 유사 사진 찾기, 장소 검색 도구를 호출해 장소를 추정하고, 코드가 후보 ID와 여행 지역을 검증
- 성과: 200장 기준 미분류 71장 → 1장, 정리 정확도(B-cubed F1) 0.637 → 0.960

**사진 정리 대기 시간 단축**

- 문제: GPU 서빙 전환 뒤에도 업로드 완료부터 정리 결과까지 AI 대기 33.2초
- 해결: 측정마다 남은 시간을 단계별로 분해해 다음 병목을 정하는 방식으로 3차에 걸쳐 개선
  - 작업 시작 비용 제거: 작업마다 반복되던 프로세스 기동과 모듈 로딩을 대기 프로세스와 .pyc 사전 컴파일로 제거, 시작 비용 5.6초 → 0.3초
  - 업로드 중 임베딩: BE와 합의한 사진 10장 단위 업로드 이벤트로 업로드가 진행되는 동안 임베딩, 29.0초 → 9.6초
  - 지표 미리 계산: 흐림(라플라시안 분산), 중복(pHash) 판정 지표도 업로드 중에 계산해 저장하고 사진 재다운로드 제거, 9.6초 → 3.6초
- 성과: AI 대기 33.2초 → 3.6초, 같은 200장에서 정리 정확도(B-cubed F1) 0.980 유지

**자연어 사진 검색 품질 개선**

- 문제: 임베딩 유사도 하나로 순위와 반환 여부를 함께 정하는데 질문마다 점수 분포가 달라 하나의 하한으로 확정할 수 없고, 정답 없는 질문에도 사진 반환. 시간대, 장소 이름 조건 미처리와 LLM의 상대 날짜("지난주 금요일") 계산 오류
- 해결
  - 질의 해석: LLM(Gemma 4 31B)은 날짜, 시간대, 장소 표현만 JSON 스키마로 추출하고, 상대 날짜 계산과 조건 판정은 코드로 처리해 후보 축소
  - 반환 기준: 절대 하한과 1위 대비 비율 컷을 개발셋에서 격자 탐색으로 재선정
  - 모델 선정: 한국어 텍스트와 사진 검색 정확도(R@1)로 다국어 임베딩 모델을 비교해 1위(65.5)인 Qwen3-VL-Embedding-2B 선택
- 성과: 검색 F1 0.34 → 0.55, 정답 없는 질문의 거절 F1 0.15 → 0.60

**생성 모델 응답 지연 단축**

- 문제: 질의 해석 정확도와 스토리 품질을 위해 생성 모델을 Gemma 4 31B로 교체하자 단독 생성 27.0 tok/s로 질의 해석이 검색 지연의 주요 구간이 됨
- 해결: vLLM 투기적 디코딩에서 MTP 초안 길이(k=1, 2, 4)별 수락률과 처리량을 같은 조건(A40, 검색 51문항 3회, 동시 4건)으로 비교해 동시 처리량이 가장 높은 k=2 채택
- 성과: 질의 해석 p50 2.75초 → 1.73초, 단독 생성 27.0 → 48.0 tok/s, 동시 4건 처리량 71.0 → 166.5 tok/s, 검색 지표와 답변 판정 결과 변화 없음

**협업**

- QA 반영: 위치 불명 사진 판정 이슈를 BE, FE 구현부터 확인해 다른 파트 수정 없이 AI 응답만 바꿔, 사용자가 직접 정리할 사진 73장 → 48장(200장 오프라인)
- BE 연동: 업로드 요청이 AI 결과가 나올 때까지 연결을 384.6초(nginx 제한의 64%) 점유하던 구조를 BE와 Kafka 이벤트 기반 비동기 처리로 전환, 중복 결과는 BE가 실행 ID로 거르도록 규칙 합의

### [paper-Pilot](https://github.com/wooseok-98/paper-Pilot) | 논문 검색 질의응답 멀티 에이전트 (2026.07 - 2026.08)

- 개인 프로젝트, 기획부터 AWS EC2 배포까지
- 기술: LangGraph, Claude API, FAISS, sentence-transformers, FastAPI, Docker, AWS EC2(ARM)
- 설계 기록: [설계 결정 기록 27건](https://github.com/wooseok-98/paper-Pilot/blob/main/docs/decisions.md), 되돌린 결정과 그 이유 포함

**프로젝트 소개**

- 논문 주제를 arXiv에서 검색해 관련 논문을 모으고, 초록을 근거로 질문에 답하는 에이전트 시스템
- Orchestrator(의도 분류), Researcher(검색 결과 필터링, CRAG), QA(초록 충분성 판단 후 재검색, Self-RAG), Critic(근거 없는 주장 검출 후 재작성, Reflection)

**에이전트별 평가 체계 구축**

- 문제: 최종 답변만 보면 라우팅 오류와 검색 오류를 구분할 수 없어 어느 에이전트를 고쳐야 할지 판단 불가
- 해결
  - 평가셋: 검색 필터, Critic, QA를 각각 채점하는 평가 스크립트와 사람이 직접 라벨링한 골든셋, 평가 대상이 LLM 필터라 LLM 채점은 자기 채점 순환으로 보고 배제
  - 재현성: 판단 호출의 temperature를 0으로 고정한 뒤 같은 스크립트 2회 연속 실행에서 전 지표 동일 재현 확인
  - 회귀 검출: 필터 프롬프트 강화로 precision 0.44 → 0.50이지만 recall 1.00 → 0.25, F1 0.61 → 0.33으로 떨어진 과잉 교정을 같은 골든셋으로 확인하고 baseline 복구, 이후 평가셋, baseline, 개선, 재측정 순서가 아니면 프롬프트를 고치지 않는 원칙 수립

**검색 개선**

- 문제: "stable diffusion" 검색에 재료과학의 확산 논문이 섞이고, 영어 전용 임베딩에 한국어 질문이 그대로 들어가 정답 논문이 상위 5편 밖으로 밀리며 재검색 반복
- 해결
  - 무관한 논문: LLM이 만든 제외 쿼리를 arXiv가 지원하지 않아, 통제할 수 없는 검색 쿼리 대신 코드로 통제하는 결과 필터(CRAG)로 이동, 원본 검색어와 공식 용어 대체 쿼리를 병행해 누락 보완
  - 한국어 질문: 의도 분류 호출에서 영어 검색어를 함께 생성해 검색에 사용, 필터에도 같은 키워드를 넘겨 기준선 측정 조건 유지
- 성과: 골든셋 20건 기준 precision 0.20 → 0.44(recall 1.00 유지), 대체 쿼리로 원본이 놓친 관련 논문 3편 확보

**근거 없는 답변 방지**

- 근거 검증: 답변의 주장을 인용 논문 초록과 대조하는 Critic, 환각을 심은 답변 3건 모두 반려, 정상 답변 3건 오탐 0건
- 답변 보류: 재검색 3회, 재작성 2회 상한에 도달하거나 외부 API 장애가 나면 보류 사유(초록 불충분, 답변 근거 없음, arXiv 장애)를 담아 답변 보류
